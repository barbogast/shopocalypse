## 1. Bugs

### B1 – Import fails on name + plural of the same item (high, confirmed)
`parseRecipeText` checks for duplicate ingredients by name only (`app/recipe-import.ts:240`). `importRecipe` then resolves names *and plurals* to item ids (`app/db/recipes.server.ts:116,136`). Take `1 Zwiebel` and `2 Zwiebeln - in Ringen` with the existing item Zwiebel/Zwiebeln. Both lines map to the same item, and the insert fails:

```
SQLITE_CONSTRAINT: UNIQUE constraint failed: recipe_ingredients.recipe_id, recipe_ingredients.item_id
```

The preview shows no error. You get the error page and lose the typed text. The "Plural of X?" button on the preview can cause this by itself: it turns two different names into one item.
**Fix:** check for duplicates by the resolved item, both in the preview and in the action. The page already has `allItems`. Build a key → id map and report `"Zwiebeln" is the same item as line 4; combine them into one line.` The action should return that as an error rather than reaching the insert.
**Status (2026-10-28):** done in `635851e`. `parseRecipeText` and `parseItemsText` take the existing items.

### B2 – A failed tick replaces the shopping page with the error page (high)
React Router sends a fetcher's error to the nearest `ErrorBoundary` (`setFetcherError` → `findNearestBoundary` in react-router's router). `shopping.tsx` has no boundary of its own, so the root one renders "Oops! An unexpected error occurred." in place of the list. This happens for a fetch that fails offline as well as for a server error. In the shop with poor reception, that is worse than the "tick is lost" the old review described.
**Fix:** this is G1 step 2 (below). Until then, a `clientAction` that wraps `serverAction()` in `try/catch` and returns `{ error }` keeps the page. Test it on the phone in airplane mode.
**Status (2026-10-22):** done with G1.

### B3 – Merging forgets the duplicate's name (medium)
`mergeItem` keeps the duplicate's *plural* if the kept item has none, but drops its *name* (`app/db/items.server.ts:239-252`). Merge "Karotten" into "Karotte", and the next import that says "Karotten" creates a new item "Karotten" again.
**Fix:** if the kept item has no plural, offer "Keep *Karotten* as its plural". Default it to on when `likelySingular` matches, or always fill it in when the slot is free. The kept item's plural can only hold one alternative name, so this covers the common singular/plural case only.
**Status (2026-10-28):** done in `09e129b`, as "fill it in when the slot is free", but only when `likelySingular` matches. A checkbox wasn't worth it, since any other name would make a wrong plural ("2 Mohrrübe").

### B4 – Deleting a recipe that's on the active list (medium)
`deleteOrArchiveRecipe` deletes the recipe's `shopping_list_recipes` rows (`app/db/recipes.server.ts:25`), but not the items they added. The items stay on the list, the meal disappears from it, and "Remove meal" can no longer take them off. It takes one tap, and nothing asks first (U1).
**Fix:** treat "on a shopping list" like "cooked" and archive the recipe instead of deleting it. The alternative is to call `changeItemsForMeals` for the active list first. Archiving is simpler and also keeps the history of completed lists intact.
**Status (2026-10-28):** done in `fe3a3df` by archiving.

### B5 – tick/untick/remove-item aren't scoped to the active list (low, carried over)
`shopping.tsx:316-341` updates by row id alone. This matters once G1 replays queued ticks, because a stale tick could land on a completed list. Add `shoppingListId = activeList.id` to the `where` as part of G1.
**Status (2026-10-22):** done with G1.

### B6 – Item renames don't record recipe versions (low)
Renaming an item, merging, or a suggestion's singular rename changes the text of every recipe that uses it, but no version is recorded. The next unrelated edit of each of those recipes then shows the rename in its diff, under that edit's date.
**Fix:** either document this in `data_model.md`, or call `recordRecipeVersion` for the affected recipes in `updateItem`/`mergeItem`. Documenting is enough unless the history page gets used a lot.
**Status (2026-10-28):** documented in `data_model.md` (`1bd832f`).

### B7 – Unexpected errors from the suggestion call (low, plausible)
`suggestItems` turns `Anthropic.APIError` into a message, but rethrows anything else (`app/item-suggest.server.ts:84-89`). An example would be an answer that fails the zod parse. Through the fetcher this is the same path as B2: the page is replaced, and the half-filled item form is lost.
**Fix:** `console.error` it and return `{ error: "Suggestions failed; try again." }`.
**Status (2026-10-28):** done in `ff3051d`, also for `transcribeRecipe` (photo import, added since).

### B8 – Rare races end in a 500 (low, no action)
`add`/`auto-fill` compute `max(position) + 1` outside a transaction (`app/routes/home.tsx:135,180`). `create-item` checks for name clashes before the insert, with the unique index as a backstop. Either one only fails when two devices submit at the same moment. `SubmitButton` already covers double taps.

## 2. Offline ticking (G1, carried over and now more urgent)

Step 1 (optimistic ticks) is done. Step 2 is still the plan:
1. Add a `clientAction` on `/shopping`. For `tick`/`untick`, write to a `localStorage` outbox, apply the outbox to the rendered list, and try `serverAction()`. On failure, keep the entry and don't throw (this fixes B2).
2. Flush the outbox on `online`/`visibilitychange`, and let a `clientLoader` merge it over the server data. Ticks are idempotent, so replaying them is safe once B5 is in.
3. Only if it's needed: add a service worker so the page *loads* offline (see the old review for the Basic Auth caveat).

Combine this with E1. If a tick no longer revalidates the whole page, the outbox also has less to fight with.

**Status (2026-10-22):** steps 1 and 2 are done, along with B2, B5 and the tick part of E1. The outbox is in `app/tick-outbox.ts`. React Router stays on 7, because `@vercel/react-router` 1.3.7 still requires it. Some details differ from the plan:
- There's no `clientLoader`. The component overlays the outbox (`useSyncExternalStore`), and each fresh load of the list drops the entries the server already has.
- Synced ticks stay in the outbox until the next load. Without a revalidation, the row would otherwise flip back once its fetcher is idle.
- `remove-item` still revalidates, for the same reason. If it fails, the row shows an error instead of the error page.
- Unsent ticks are resent on load, on `online`, when the page becomes visible, and every 30 s. The header shows "N not saved yet".

## 4. Efficiency

### E1 – Each tick reloads the whole shopping page (medium)
After every fetcher submit, the full loader runs again (`shopping.tsx:73-176`). That's 10 sequential queries: the active list, the schedule, the list items, **all items**, the list's recipes, their ingredients, all recipes, stores, shelves and parents. Each one is a round trip to Turso, on the phone's connection, in the shop.
**Fix:** add `shouldRevalidate` that returns `false` when `formData.get("intent")` is `tick`, `untick` or `remove-item`. The optimistic UI already shows the result. The cost is that another device's changes show up only on the next navigation. That fits with the "Auto-refresh for shopping list" idea in `TODO.txt`, which would handle it with a targeted poll.
**Status (2026-10-22):** done for `tick`/`untick` with G1. `remove-item` still revalidates (see section 2).

### E2 – Loaders query sequentially (low)
The independent queries in `shopping`, `recipes.$id`, `home` and `items` could run in a `Promise.all`. Measure first, since in `fra1` each round trip is probably a few ms. This matters less once E1 is in.

## 5. Tests

### T1 – No tests reach the database
The pure modules are well covered: units, list building, import, diff, sanitizing. The code that has the bugs isn't covered:
- `mergeItem`
- `importRecipe`
- `deleteOrArchiveRecipe`
- `recordRecipeVersion` (session folding and undo)
- `applySuggestions`
- the auto-fill order

libSQL makes testing these cheap:
1. A vitest `setupFiles` entry points `DATABASE_URL` at a fresh temp file and runs drizzle's `migrate()` on it once.
2. Each test then imports `~/db/...` as normal.

B1 was confirmed exactly this way, as an ad-hoc test against a copy of `shopocalypse.db`. Start with a regression test for B1, then `mergeItem` and `deleteOrArchiveRecipe`.
**Status (2026-10-28):** started in `09e129b`. A test file imports `./test-db` first, which points the client at a fresh, migrated temp file (no `setupFiles`, so the pure tests don't pay for it). `mergeItem`, `importRecipe` and `deleteOrArchiveRecipe` are covered, and B3 and B4 have regression tests. B1 is tested in the parser, where its fix is. Still open: `recordRecipeVersion`, `applySuggestions` and the auto-fill order (which needs O1's extraction first).
